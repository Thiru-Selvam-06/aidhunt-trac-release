Baseline bb0ed289e636f6ded79ed075fd860f92effe34c8 on codex/phase45-notification-pilot. Phase 5 is an in-app view in the existing notification bell. The Live Test package is com.aistudio.aidhunttrac.cedlir.livetest, with native push disabled.

## What the app does

Each installation keeps a separate last successful server checkpoint for each original Owner UID and workspace ID. Android's foreground lifecycle starts a visit. The app keeps that visit's starting checkpoint through recomposition, navigation, subsequent notifications, and reconnects. A configuration change does not start a visit. When the process ends, the last persisted successful server read acts as the checkpoint for the next visit. First sign-in establishes a baseline after a successful refresh and shows imported recent history without labeling it as new. Initial history queries cover up to 31 days. Already saved notification history is not truncated by the refresh.

The Owner's authenticated Firebase ID token and App Check, when available, authorize read-only requests. The app verifies the workspace ownerUid and active Owner membership. It accepts only supported ledger evidence attributed to other active Partners in that workspace. The existing listeners signal refreshes when authoritative ledger or notification rows change. Bursts are coalesced and there is no new persistent listener. The refresh updates Room with stable ID keys and retains existing read flags. Only after the read and Room merge succeed does it save the Firestore server read timestamp. An interrupted refresh is safe to repeat. Offline and failed refresh states show cached activity and do not advance the checkpoint. Opening the bell does not mark anything read. Read and visit state for verified activity are independent across devices. Existing targeted notification behavior is retained.

Spark's currently active policy denies the client notification and audit collections. On configurations where notification history is readable, the app can preserve the read flag of a legacy row when its recipient, actor, entity, action and operation ID match verified evidence. A standalone client-generated notification or audit row does not prove a financial commit. Old stored rows are retained; unsupported or uncorroborated rows are not promoted into verified Owner activity. No plan, Rules, Auth, Firestore write protocol, notification publisher, or financial calculations were changed. ## Coverage and known gaps

| Partner action | Recoverable when | Where a delayed Owner refresh may miss it |
| --- | --- | --- |
| New Entry and Old Entry | The initial confirmed entry still holds its original actor and operation, and includes the historical flag. | A job edit, an initial payment or removal can replace the original operation metadata before the Owner sees it. |
| Job edit | The confirmed job edit audit or guarded deletion proof retains actor, operation, action time and before/after. | Legacy writes without an audit are skipped. A very late offline edit may appear in History instead of Since Your Last Visit because its nested audit contains action time but no separate server commit timestamp. |
| Job delete | A guarded deletion leaves an immutable entryDeletionProof containing the exact delete operation. | A path that lacks a proof is skipped. A proof is queried by action time, with a one-day overlap, and exceptionally old offline proofs can fall outside the query. |
| Collection and reversal | The confirmed collections row has the active or reversed operation. Atomic cash receipts can additionally corroborate covered paths. | A later reversal replaces a prior non-cash collection operation. A removed receipt may lack retained history. |
| Expense added and edited | The confirmed expense still has the original creation or most recent edit operation, distinguishable by Firestore creation and update metadata. | Rapid edits overwrite earlier operations. A compatibility hard deletion removes the source. |
| Expense delete | A matching atomic cash deletion proof remains readable for the workspace. | The compatibility two-step delete does not retain a proof after the expense is hard-deleted. The intermediate tombstone is skipped. |
| Ordinary withdrawal | A confirmed ordinary withdrawal remains, or a covered atomic cash receipt still identifies it. | A compatibility delete can remove the original source. Borrowing and settlement actions are excluded. |

Reference text comes from the authorized record where available. Otherwise the bell displays the transaction type and ID. Customer-entered names and labels are preserved. Timestamps use Asia/Kolkata and the Owner's English or Tamil language.

## Local verification

The focused run passed 140 Android JVM tests, with zero skips or failures, while the synthetic Firestore Emulator was running. It included Kotlin activity, visit-boundary and IST/English/Tamil tests, a Compose status test, a persistent Room restart and independent-device cache test, an authenticated Owner query test, and the existing notification, authorization, deletion, collection and acknowledgement regressions. Emulator credentials and transaction records were synthetic.

The already registered Live Test package was verified active in trac-aidhunt. Read-only checks using both synthetic sign-ins verified the original Owner, the scope of the pilot, Firestore's server read timestamp, and the separate range query shapes under the deployed policy. ## Controlled two-phone checklist

All checks below are **NOT TESTED on physical phones** until someone runs them. Use only the synthetic TRAC Notification Pilot workspace. The authorized test identities are **TRAC Pilot Owner** (Phone 1) and **TRAC Pilot Partner** (Phone 2). Use the pilot email sign-in and the existing protected pilot credentials. Do not sign in using a customer's or real business account. Do not create a new business from the test build.

| Step | Action | Expected result and evidence |
| --- | --- | --- |
| 1. Install | Open the internal Live Test APK on both phones. Leave the regular TRAC app and its data in place. If Android reports a signing conflict with an existing Live Test install, stop and record the message. | The separate package installs. The regular TRAC entry remains accessible. Save a screenshot of Android App info for the test app. |
| 2. Establish the baseline | Sign in as the synthetic Owner on Phone 1. Verify the pilot workspace name. Open the bell with internet, wait for Last Updated, and record the timestamp. Close the bell and leave the app on the Android launcher. | The first verified refresh establishes a baseline. Prior history is not labeled as new. No need to grant Android push permission. |
| 3. Create and observe | On Phone 2, sign in as the synthetic Partner. Add an unpaid job with a clearly synthetic customer label. Wait for the job to sync. On Phone 1, reopen TRAC and check the bell. | The bell shows the Partner and new job, with a reference if available, an IST timestamp and an unread indicator. Save the Owner bell screenshot and the Partner sync status. Observe the creation before editing the job to check that separate event. |
| 4. Edit and collect | Leave TRAC on Phone 1 again. On Phone 2 edit the test job and record a partial test collection. Confirm both cloud writes. Foreground Phone 1. | The verified job edit and collection appear. Work time and recording time remain distinct. The existing Job and Customer Due amounts match the synthetic actions. |
| 5. Read state and restart | Open and close the bell without tapping any row. Reopen it. Tap only one unread row, then exit and reopen the app. | Opening the bell does not clear unread flags. The one tapped row stays read across restart. Other events remain unread. History shows each event once. |
| 6. Partner reconnects | On Phone 2 turn off internet, add an unpaid synthetic job, and leave it pending. Keep Phone 1 online and refresh there. | 7. Owner reconnects | After a successful Owner visit, take Phone 1 offline and reopen it. Leave Phone 2 online and add a personal synthetic expense. Reconnect Phone 1. | Cached notifications and unread flags remain visible while offline. Last Updated does not move while offline. The new expense appears after refresh, if its committed source is still present. |
| 8. Tamil and small screen | In the Owner's test app switch to Tamil, then repeat a foreground refresh and one read action. Scroll both sections on the smaller handset. | Labels are legible Tamil, existing names remain unchanged, timestamps are IST, and read state does not reset. |
| 9. Known missing history | With Phone 1 away, add and edit a synthetic expense multiple times before reconnecting Phone 1. If separately trying a synthetic compatibility delete, verify that the record disappears from the Partner's synced ledger. | An earlier expense version or completed hard delete without a retained proof may be absent. This is the existing history limit. If a still-verifiable action is absent despite a successful Owner refresh, capture the action, operation ID if available, and both phone timestamps as a refresh issue. |
